# Requirements: SP-2

Source: input/story.md (snapshot hash recorded by the orchestrator)
Status: draft (revision 1)

## Summary
Smart Pantry Organizer is a web application for an individual household to manage its pantry inventory. It covers grocery item CRUD, category organisation, expiry tracking, a dashboard summary, rule-based recipe suggestions from predefined recipe data, and search and filtering. Requirements below are derived from story sections 3, 4, 6 and 7; open points are listed under Open questions and are not decided here.

## Functional requirements
| ID | Requirement | Acceptance criteria |
|---|---|---|
| REQ-001 | The application lets a user add a new grocery item with item name, quantity, category, purchase date and expiry date. (FR-01, AC-01) | A valid item submitted through the add form is saved and appears in the inventory list; an item with missing or invalid mandatory fields is not saved and the user sees a meaningful validation message per field. Which fields are mandatory is open (Q-001). |
| REQ-002 | The application lets a user view all saved grocery items. (FR-01, AC-02) | The inventory list shows every saved active item, and each row shows the item's name, quantity, category and expiry information. |
| REQ-003 | The application lets a user view the details of an individual grocery item. (FR-01) | Selecting an item opens a detail view showing all stored fields of that item (name, quantity, category, purchase date, expiry date, expiry status). |
| REQ-004 | The application lets a user edit the details of an existing grocery item. (FR-01, AC-03) | After editing and saving a valid change, the new values are shown in the item detail view and the inventory list; an invalid edit is rejected with the same validation messages as REQ-001. |
| REQ-005 | The application lets a user delete an existing grocery item. (FR-01, AC-04) | After deletion, the item no longer appears in the inventory list, search results, filter results, or dashboard counts. Whether deletion is permanent or recoverable is open (Q-012). |
| REQ-006 | Grocery items are persisted in a database. (NFR-03, FR-01) | An item added or edited is still present with identical field values after the application is restarted. |
| REQ-007 | Every grocery item belongs to exactly one category from the set Vegetables, Fruits, Dairy, Grains, Snacks, Others. (FR-02, AC-05, BR-5) | Saving an item with no category, or with a category outside the set, is rejected with a validation message; each item's category is displayed in the list and detail view. |
| REQ-008 | The application lets a user filter pantry items by category. (FR-02, AC-05) | Selecting a category shows only active items whose category equals the selected category; selecting no category shows all items. |
| REQ-009 | The application accepts an expiry date entered by the user when adding or editing an item. (FR-03) | A valid calendar date is accepted and displayed in the item's expiry information; a value that is not a valid date is rejected with a validation message. (BR-3) |
| REQ-010 | The application identifies expired items. (FR-03, AC-06, BR-4) | An item whose expiry date is earlier than the current date is classified as Expired. The boundary case (expiry date equal to today) is open (Q-003). |
| REQ-011 | The application identifies items approaching their expiry date. (FR-03, AC-06) | An item whose expiry date falls within the "approaching expiry" window is classified as Expiring soon. The window length is not defined in the story; see Q-002. |
| REQ-012 | The application shows a visual indicator that distinguishes Expired, Expiring soon and Valid items. (FR-03, BR-4) | Each of the three statuses renders a different indicator (for example a different colour or label) in the inventory list and detail view, and an item's status can be read from the indicator without opening it. |
| REQ-013 | The application displays expiry information clearly on item views. (FR-03, AC-06) | The inventory list and detail view each show the expiry date and the expiry status for every item that has an expiry date. |
| REQ-014 | The dashboard shows the total number of active grocery items. (FR-04, AC-07) | The dashboard count equals the number of active items in the inventory list. |
| REQ-015 | The dashboard shows total inventory quantity where applicable. (FR-04) | The dashboard total equals the sum of quantities of the active items it covers. Which items are covered and how mixed units are handled is open (Q-004). |
| REQ-016 | The dashboard shows the items approaching expiry. (FR-04, AC-07) | The dashboard lists or counts exactly the items classified as Expiring soon under REQ-011. |
| REQ-017 | The dashboard shows the expired items. (FR-04, AC-07) | The dashboard lists or counts exactly the items classified as Expired under REQ-010. |
| REQ-018 | The dashboard shows a category-wise inventory summary. (FR-04, AC-07) | For each category in REQ-007, the summary shows the item count and quantity total, and the category totals sum to the overall totals in REQ-014 and REQ-015. |
| REQ-019 | Changes to inventory are reflected in the dashboard. (BR-7, AC-07) | After an item is added, edited or deleted, the dashboard values shown on the next dashboard view match the updated inventory. The refresh timing is open (Q-018). |
| REQ-020 | The application suggests recipes that can be prepared from the ingredients currently in the pantry. (FR-05, AC-08) | A recipe is listed as makeable only when every required ingredient of that recipe matches an active pantry item; a recipe with at least one unmatched ingredient is not listed as makeable. The matching rule is assumed (A-003) and its strictness is open (Q-009). |
| REQ-021 | For each suggested recipe, the application displays the full list of ingredients required. (FR-05) | Each suggested recipe view shows every ingredient in that recipe's predefined definition. |
| REQ-022 | For each recipe that is not fully makeable, the application identifies the missing ingredients. (FR-05, AC-08) | The missing list for a recipe equals its required ingredients minus the active pantry items; a fully makeable recipe reports no missing ingredients. |
| REQ-023 | Recipe suggestions give priority to recipes that use pantry items approaching expiry. (FR-05) | Among suggested recipes, a recipe that uses at least one Expiring soon item is ordered before a recipe that uses none, all other factors equal. The full ranking rule is open (Q-010). |
| REQ-024 | Recipe suggestions use rule-based matching against predefined recipe data, with no call to an external AI API. (FR-05, BR-6, BR-8, Section 9) | Recipe suggestions are produced from the predefined recipe dataset; a test confirms that suggestion generation makes no external AI API call and works with no external AI service available. |
| REQ-025 | The application lets a user search grocery items by name. (FR-06, AC-09) | Searching for a text value returns and displays only active items whose name matches that text; an empty search returns the full inventory. Matching rules (case, partial match) are open (Q-007). |
| REQ-026 | The application lets a user filter items by expiry status. (FR-06, AC-09) | Selecting Expired, Expiring soon or Valid shows only active items with that status, as defined by REQ-010 and REQ-011. |
| REQ-027 | Search and filter results are shown in the same view as the inventory, without requiring the user to page through the full inventory. (FR-06) | After one search or filter action, the matching items are displayed on the inventory screen and no separate navigation step is required to see them. |
| REQ-028 | The backend rejects an item whose name is missing or empty. (BR-1, NFR-05, AC-10) | A create or update request with an empty or missing item name is rejected by the backend with an error response and the item is not stored, even when the frontend validation is bypassed. |
| REQ-029 | The backend rejects an item whose quantity is not a valid positive value. (BR-2, NFR-05, AC-10) | A create or update request with a quantity of zero, a negative value, or a non-numeric value is rejected by the backend with an error response and the item is not stored. The allowed numeric type is open (Q-004). |
| REQ-030 | The backend rejects an item whose expiry date (or other date) is not a valid date. (BR-3, NFR-05, AC-10) | A create or update request containing a date that is not a valid calendar date is rejected by the backend with an error response and the item is not stored. |
| REQ-031 | The backend rejects an item whose category is not in the REQ-007 set. (BR-5, NFR-05, AC-10) | A create or update request with a category outside the allowed set is rejected by the backend with an error response and the item is not stored. |
| REQ-032 | API errors are handled gracefully and shown to the user as readable messages. (AC-10, NFR-03, NFR-05) | When an API call fails (for example, the backend returns an error or is unreachable), the user sees a readable message, and no stack trace, internal class name or configuration value is displayed. |

## Out of scope
- Paid external AI integrations.
- Online grocery ordering.
- Payment processing.
- Multiple household member accounts.
- Advanced machine-learning-based recipe recommendations.
- Third-party grocery delivery integrations.
- Technology stack choices (Section 5 of the story). These are preferences recorded as context and are not requirements; architecture is for the architecture agent and human approval.
- Deliverables in Section 8 (REST API documentation, setup instructions, technical documentation, GitHub repository) are treated as deliverables, not functional requirements, unless the project owner says otherwise (Q-019).

## Assumptions
- A-001: The application serves a single individual household; there is one user context and no multi-user accounts, since multiple household accounts are out of scope (Section 9).
- A-002: No login or user authentication is required in the initial version, because the story does not specify one. This is inferred from A-001 and is not stated as a fact (see Q-017).
- A-003: "Can be prepared using available ingredients" means every required ingredient of a recipe matches an active pantry item by name; quantities of recipe ingredients are not compared. Assumed because the story does not define it.
- A-004: The recipe catalogue is predefined and shipped with the application; users do not create or edit recipes in the initial version.
- A-005: "Today" for expiry classification is the current system date at the time the view is rendered.
- A-006: Quantity is a numeric count of an item; the unit of measure is not stored as a separate requirement. Assumed because the story does not define units.
- A-007: Duplicate item names are permitted, since the story does not state a uniqueness rule.
- A-008: The category set in REQ-007 is fixed; users cannot create custom categories.
- A-009: The product is a browser-based web application; no native mobile app is in scope, as the story says "Web Application".
- A-010: The database technology named in Section 5 (H2) and the other stack preferences are context only and do not constitute requirements; they are not reflected as REQ entries.
- A-011: Expiry status (Expired, Expiring soon, Valid) is derived from the expiry date and the current date, and is not entered manually by the user.

## Open questions
- Q-001: Which add/edit fields are mandatory? The story says "required details" (AC-01) but does not list them. Is expiry date mandatory, or may an item have no expiry date?
- Q-002: What is the window for "approaching expiry" (for example, number of days before expiry)? Is it fixed or user-configurable?
- Q-003: On the expiry date itself, is an item Expired or Expiring soon?
- Q-004: What type is quantity (integer or decimal) and what units apply? How is "total inventory quantity where applicable" calculated when units differ, and which items are excluded?
- Q-005: Is there a rule for purchase date (for example, must it be on or before the expiry date, or may it be in the future)?
- Q-006: How should items without an expiry date be displayed and classified in the dashboard and filters?
- Q-007: For name search, is matching case-insensitive and partial (substring), or exact?
- Q-008: Can search, category filter and expiry filter be combined in one result set?
- Q-009: For recipe matching, must all ingredients be present, or may a recipe be suggested with a tolerance for missing ingredients? How are ingredient names matched (plurals, synonyms, units)?
- Q-010: What is the exact ranking rule for recipes that use Expiring soon items, and how many recipes are shown?
- Q-011: How many predefined recipes are required, who maintains the recipe data, and is adding recipes through the UI in scope?
- Q-012: Is deletion permanent, or should it be recoverable or require confirmation?
- Q-013: What numeric performance limits apply: response time for inventory load and search, and the "normal household inventory volume" to test against?
- Q-014: What usability measures apply: a maximum number of steps per common operation, and how is usability verified?
- Q-015: Which screen sizes or viewport widths (desktop and mobile) and which browsers must be supported?
- Q-016: Which coding standard and review method define "clean code" and "consistent naming", and is there a test coverage target for NFR-019?
- Q-017: Is any login or access control needed in the single-household version, and what does "appropriate data access boundaries" mean in practice?
- Q-018: How quickly must the dashboard reflect inventory changes (immediately on next view, or on a refresh action)?
- Q-019: Are the Section 8 deliverables (REST API documentation, setup instructions, technical documentation, repository) to be tracked as requirements, or treated only as delivery items?
- Q-020: Is item name uniqueness required, or may two items share a name (see A-007)?
- Q-021: Is a language or localisation requirement needed for UI text and error messages?
- Q-022: Should the application record change history for item edits, or is that out of scope?
