# Design review: SP-2

Reviewed: architecture.md (revision 1)
Round: 1
Open high-severity findings: 0

## Checks applied
- Coverage: All 32 REQ IDs (REQ-001 to REQ-032) and all 19 NFR IDs (NFR-001 to NFR-019) appear in the requirement-to-component map. No ID is missing. Mapping errors are recorded in DR-002, DR-003 and DR-004.
- Responsibility: 15 components reviewed. Overlap between Item service and Item query service for the inventory list is recorded in DR-004.
- Failure modes: External calls are limited to H2 and the recipe data file. Frontend unreachable or backend error handling (REQ-032) is adequately handled. H2 and recipe-file failures are not designed (DR-009).
- Empty and missing data: Empty search, empty dashboard and no-expiry items are partly covered. The no-expiry case is not designed in the classifier (DR-005).
- Security: Backend validation at the boundary (REQ-028 to REQ-031) and sanitized errors (REQ-032, NFR-013) are adequately handled. Auth is an accepted risk (Q-017). H2 console and bind address are not stated (DR-013).
- Data integrity: Single owner (Item service) for writes is stated. Concurrent edit behaviour is not stated (DR-012).
- Testability: Injected Clock supports date tests. Performance tests for NFR-003 to NFR-005 are not assigned to any suite (DR-010).
- Dependencies and technology risk: JaCoCo is justified for NFR-019 and flagged for CP2 (DR-015). H2 file-mode risks are not named (DR-016).
- Scale and performance: No caching; per-request classification at 1,000 items is a named risk. Adequate as a risk, but needs the test in DR-010.
- Operability: No server-side logging or diagnosis path is designed (DR-011).
- Architect's points: Q-012 (DR-008), REQ-023 tie-break (DR-001), A-005 clock (DR-006), A-003 normalisation (DR-007), JaCoCo (DR-015). Each is covered by a finding below.

## Findings
| ID | Severity | Concerns | Description | Proposed fix | Disposition |
|---|---|---|---|---|---|
| DR-001 | medium | REQ-023; Recipe suggestion service | REQ-023 defines two ranking keys (Expiring soon use, then fewest missing). Recipes equal on both keys have no defined order. The output order is then non-deterministic, so the "all matches shown" result cannot be tested exactly for that case. The architecture leaves this open. | Architect adds a deterministic final key (for example recipe name ascending, case-insensitive) and records it as an assumption for human confirmation at CP2. Requirements owner may instead decide the key. | |
| DR-002 | medium | REST API layer; REQ-001 to REQ-027 | The REST API layer's component row and the requirement map list it only for REQ-028 to REQ-031 and NFR-010/012/015. Data flow steps 4 to 9 route every read and write through it, including the recipe endpoint that serves REQ-020, REQ-022 and REQ-023. Endpoint ownership for most requirements is therefore untraced. | Add REST API layer to the map rows for REQ-001 to REQ-027 that are served over HTTP, and list the recipe suggestion endpoint explicitly. | |
| DR-003 | medium | Browser screens; REQ-015 to REQ-018, REQ-020, REQ-022 to REQ-026 | Browser screens is not listed for the dashboard totals and lists (REQ-015 to REQ-018), recipe suggestions and missing ingredients (REQ-020, REQ-022, REQ-023, REQ-024), search (REQ-025) or the expiry filter (REQ-026). The component responsibility does not name these screens, so no component owns the UI for these requirements. | Add dashboard, recipe and search/expiry-filter screens to the Browser screens responsibility and to the requirement map rows. | |
| DR-004 | low | Item service; Item query service; REQ-002, REQ-024, REQ-028 to REQ-031 | (a) REQ-002 (list all items) is not assigned to a single service. Item service has "read", and Item query service returns filtered lists, so the inventory read is duplicated. (b) REQ-024 map omits Test suites, which must carry the no-AI-call test. (c) REQ-028 to REQ-031 map omits API error handler, which converts validation failures to error responses. | (a) State that the inventory list uses Item query service with an empty filter, and that Item service reads a single item for the detail view. (b) Add Test suites to REQ-024. (c) Add API error handler to REQ-028 to REQ-031. | |
| DR-005 | medium | Expiry classifier; REQ-010, REQ-012, REQ-013, REQ-026 | The architecture does not say how an item with no expiry date is classified. REQ-026 excludes such items from all expiry filters, including Valid. If the Valid filter is written as "not Expired and not Expiring soon", null-expiry items are wrongly included. | State in the Expiry classifier that a missing expiry date yields no date status (shown as Valid indicator, "No expiry date"), and that date bounds for Valid and the other statuses explicitly exclude null expiry dates. Add a test case for each. | |
| DR-006 | medium | Expiry classifier; A-005; REQ-010, REQ-011, REQ-001, REQ-030 | The design chooses the server clock. It does not state the time zone. A server running in UTC and a household in another zone can disagree near midnight, so an item can change status on a different day than the user expects. The same clock is used by the purchase-date rule (REQ-030). | Inject a Clock bound to an explicit configured zone (documented in setup). Record A-005 as a decision for the human to confirm at CP2: server clock with a named zone, or browser date. | |
| DR-007 | medium | Item validator; Recipe suggestion service; A-003; REQ-020, REQ-022, REQ-028 | Matching is "case-insensitive on the exact name". Leading or trailing spaces, repeated internal spaces and Unicode case folding are not defined. "Milk " will not match "milk", so a recipe is wrongly marked not makeable. A whitespace-only name also passes the plain "empty" check in REQ-028. | Define one normalisation rule (trim, collapse internal whitespace, case-fold with Locale.ROOT). Apply it to pantry names on save (reject whitespace-only names under REQ-028) and to recipe ingredient names at match time. Record the extension for human confirmation alongside A-003. | |
| DR-008 | low | Item repository; Item query service; Dashboard service; REQ-005, REQ-014, REQ-025 | Q-012 check: every stored item being active is consistent with permanent delete. REQ-005 says delete is permanent, and there is no inactive state, so all stored items are active. The architecture's open question is already decided, so it is out of date. The "active" wording is redundant and would mislead a later change, such as adding soft delete. | Remove the open question. State that stored items are the active inventory because delete is permanent (REQ-005). Note that introducing any inactive state later requires revising the query, dashboard and recipe rules. | |
| DR-009 | medium | Recipe catalogue; H2 database; NFR-003, NFR-006, REQ-024, REQ-006 | Failure modes are not designed. (a) The recipe data file may be missing, malformed or empty; the design does not say whether this fails at startup or per request, or what the suggestion endpoint returns. (b) H2 file may be locked by a second process, unavailable or corrupt; no startup or request behaviour is stated. | (a) Load and validate the file at startup and fail fast with a logged reason. Define an empty-catalogue response. (b) Define startup failure on lock or corruption, and a sanitized 503 for request-time DB failure (REQ-032). | |
| DR-010 | medium | Test suites; NFR-003, NFR-004, NFR-005, REQ-024 | Test suites lists unit, integration, REST and browser tests only. No component carries the performance test that NFR-003, NFR-004 and NFR-005 require at 1,000 active items. The no-AI-call test for REQ-024 is also not assigned. | Add a performance test (seeded 1,000-item data set, timed list, search and filter) to Test suites. Assign the REQ-024 no-network test to Test suites. | |
| DR-011 | medium | API error handler; REST API layer; NFR-007, NFR-013; Operability | Errors are sanitized for the client, but the design does not say how a server-side failure is diagnosed. There is no logging, correlation ID or rule that keeps secrets and SQL out of logs. A failure cannot be traced from a user report. | Log every handled failure server-side with a correlation ID that is also returned in the sanitized response. Log no secrets, SQL or stack traces to the client. State the log destination. | |
| DR-012 | low | Item service; REQ-004, REQ-005; Data integrity | Concurrent edit and delete of the same item are not addressed. Two tabs or devices can overwrite each other silently, and an edit can target an item deleted in the meantime. | Either add a version field with optimistic locking and a 409 response for stale edits and a 404 for missing items, or record last-write-wins as an accepted behaviour. | |
| DR-013 | low | REST API layer; Application shell; NFR-015, NFR-014; Security | With no authentication (accepted for Q-017), the design does not state the network bind address or whether the H2 web console is enabled. Either would expose all data to any reachable client. | Default the server to bind to localhost unless configured otherwise. Disable the H2 web console outside a development profile. State both in the Application shell. | |
| DR-014 | low | Diagram; Data flow step 3; Item validator | Data flow step 3 has the REST API layer pass the payload to the Item validator. The diagram shows the validator called only from Item service. | Align the diagram with data flow step 3, or correct step 3 so that the validator call is made where the diagram shows it. | |
| DR-015 | low | Test suites; JaCoCo; NFR-019; Technology choices | JaCoCo is justified and flagged for CP2 approval, which is adequate. If CP2 does not approve it, the design names no fallback, yet NFR-019 requires a measured coverage report. The architecture does not confirm that the story's stack preferences exclude JaCoCo (the architect's statement is taken as given). | Name a fallback coverage tool for CP2 to choose from, or state that NFR-019 cannot be verified without a coverage measurement tool. | |
| DR-016 | low | H2 database; Risks; Technology choices | Known risks of file-mode H2 are not named: single-process file locking, file backup and recovery, and suitability for a long-running service. | Name these risks in the risks section with a mitigation (single backend process, documented backup of the database file, pinned H2 version). | |
